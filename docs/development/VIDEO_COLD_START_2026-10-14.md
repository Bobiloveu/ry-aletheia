# 新车视频冷启动与恢复

用户提供的 `video-runtime(1).log` 包含多个运行批次。10 月 13 日 20:39–20:40，六路实际通过 NVENC 发布 H.264，并建立 WebRTC 读取会话；这不能证明浏览器持续解码正常。10 月 14 日 09:58–10:24，四路 SHM JPEG 与两路 DDS BGR 输入均到达，但没有媒体发布记录，累计 2862 次本地写管道超时，中位耗时约 2.007 秒，对应原生启动写入的两秒期限。

补充 `test.txt` 的显卡为 RTX A2000 Laptop GPU 8GB，驱动 580.173.02，64 位 libcuda.so.1 与 libnvidia-encode.so.1 均存在。该文件显示时间为 6 月 5 日，与故障日志不同，不能当作同次故障时的驱动状态。当前没有实车 GStreamer 详细输出，尚未确认 CUDA/驱动内部阻塞原因。

本轮修正：

- 原生管线使用一次约十秒的初始化窗口，首次写完整帧不代表初始化结束；窗口末尾保底正常 250ms，之后持续使用 250ms 背压期限。取消仍在写循环中即时检查。
- 管线故障按 1/2/4/8/16/30 秒退避，只恢复该路；持续成功提交满六十秒才重置，超过五秒无提交重新起算。读源保持打开，只保留最新输入槽，避免重试时重复打开 SDK。
- NVENC 输入依次启动，上一流经 MediaMTX 确认发布或十二秒等待到期后继续下一路；关闭或崩溃释放当前启动等待。仅启动期间最多每秒检查一次发布状态，完成后无额外常态轮询。
- NVENC 合成编码预检放宽到十秒，VAAPI 保留四秒；均可取消。Intel 优先与硬件编码策略、现有帧率/分辨率/码率预算不变。
- 默认收集 GStreamer warning/error，保留人员明确配置的 GST_DEBUG。日志区分创建编码子进程、完整提交首帧与实际媒体发布，避免把下游超时描述成输入格式不兼容。

契约消费者为 Backend/Web/Mobile；无新增 API 必填字段或枚举，不要求额外 Mobile 工具链。本次源码仅修改 Backend/native 及必要契约、测试与文档。

验证：

- 合成消费端延迟 2.4 秒读取：原两秒写期限复现 `errno=110`，修正策略可完整提交 640×480 RGB 帧。
- 原生两项 CTest 通过，覆盖启动窗口、运行期限、背压、退避、连续健康判定、取消及子进程回收。十秒等待中的取消在 250ms 内结束。
- 官方 Backend 入口按 `-k video` 检查：65 通过、1382 未选中；离线检查 109 通过；Backend Doctor 通过。
- 实际 ROS 视频节点编译通过。构建环境没有 NVIDIA GPU，不声称完成 NVENC 实车验收或资源百分比优化。
- 独立代码复核发现并修正启动窗口末尾期限过短问题，最终复核无重要问题。

本地生成 `releases/2.8.5-shm/` 升级 ZIP 与首次安装 DEB。校验升级签名、SHA256、版本、ZIP/DEB 二进制一致性、包内 Python 与当前源码一致性、包内 native 与当前构建一致性及 ShmSDK/auto 默认配置。未安装到机器人，也未重启机器人依赖。

现场验收应先确认预检通过，再逐路确认 H.264 发布与浏览器实际解码，最后开启六路观察持续帧率、延迟及资源；如果仍失败，收集新版视频日志中的 GStreamer 错误及同期 nvidia-smi。保持运行期限和退避，不以无限等待掩盖驱动阻塞。
