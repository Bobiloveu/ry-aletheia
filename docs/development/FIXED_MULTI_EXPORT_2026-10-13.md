# 固定线路遵循项目任务模式

原固定线路分支始终输出 `tasks/<小区名_线路名>.json`，并把预览模式记为 `fixed`，
因此即使项目已选择 `multi`，保存设置、预览缓存和 ZIP 下载仍会得到单任务结构。
固定线路是任务的业务意图，`single/multi` 是输出格式，两者现在分别处理。

单任务点模式保留原整条任务格式。多任务点模式在完成原有地图可达性、设备、仓控和
定位校验后，把连续同图、同方向的子任务无损合并为四个既有运行时分段。例如当前项目：

```text
multi_tasks/高科一号演示/
  sub_outdoor_eguard.json
  sub_outdoor_eguard_r.json
  floor/1_1_n_n09.json
  floor/1_1_n_n09_r.json
```

每个文件的根对象严格只有 `change_loc`、`map_url`、`pcd_url`、`subtask_name`、`waypoints`。
公共正程包含起点、门口过渡点、取货及乘梯；楼层正程包含到达后关梯门及送货；正返段的
路点顺序、坐标、朝向、速度、任务标记和 XML 引用保持原有序列。公共返程不重放仓控，
完成事件仍在最终返抵起点时发出。公共段的目录由保存的部署阶段角色决定：摆渡层沿用既有
`sub_outdoor_eguard[ _r ].json`，电梯大厅使用 `indoor/<building>_<unit>[ _r ].json`。
摆渡地图中放置电梯组件不会把地图改成室内首层，也不复制动作到两个目录。
阶段分配、定位绑定和地图实例角色必须一致；不能悄悄跳过或重排保存的地图阶段。

多任务 XML 保留运行时目标获取：去程沿用 `n_x`，返程沿用 `x_n`，返抵源地图使用
`close_elevdoor_n`。地图切换、轮式里程计及恢复坐标均验证目的地图归属。送货节点获取
`delivery_code` 并以它发布状态；货舱和操作码仍由该线路访问配置决定，不替换成自动卸货。
标准层使用现有 `n_nXX` 命名规则；非标准层使用具体按钮层与完整门牌。楼层物理索引继续
由既有电梯按钮序列计算，不混淆按钮标签与零基物理层号。

现有 R6B 文件族无法表达任意固定行程。目前多任务固定线路要求一个公共源图、一个连续
用户楼层段、一个末端送货目标和唯一共享物理电梯；公共源图可以有多个取货点及过渡点。
多个楼层送货目标、重复目标访问或送货后切回公共图取货必须明确报错。单任务结构继续
支持其原有任意有效固定线路；多任务失败时不会改用单任务输出。

预览清单 `task_mode` 现在为 `single/multi`，`compiler_profile` 与 `active_task_line`
继续标识固定线路。预览保留完整 `subtasks` 供 Web 地图核验，但不将这个包装 JSON 写入
多任务 ZIP；`multi_task_files` 记录四个文件的实际执行顺序。固定线路多任务 ZIP 使用
`小区名_线路名_multi_experimental.zip`，行为树仍使用英文动作名及可读序号。

Backend 同时核对模式与任务目录，Web 核对预览模式及产物目录；旧单任务缓存不能作为
多任务预览复用或下载。新序列化模块纳入编译代码指纹，旧实验包保留，重新生成才获得新结构。

验证使用合成项目和当前现场项目的临时副本：四个文件扁平化后的全部导航节点等于原整条
任务。后续补齐窄通道节点、直接返程及起点朝向修正后，按当前编译输出重新核验。
检查了仓控参数、去返动作、动态楼层与配送码、
地图恢复参数、标准／非标准层命名、目录发现、模式切换和下载 ZIP。原项目与现场地图未修改。
