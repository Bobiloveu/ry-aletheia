# 全小区多任务点部署编译设计

## 状态与目标

**状态：已实施，待现场确认。**

部署建图当前的实验编译器只生成室内两图、单目标的组合任务。该能力扩展为两种互相隔离的项目模式：

- **单任务点模式**：每一个目标点生成一份从首图起点到该目标、再返程的完整任务 JSON。
- **多任务点模式**：同一条配送路线中的公共地图段拆为可复用子任务文件；每个目标点只生成独立的用户楼层正返程文件。

两种模式均服务一个完整小区，不限制为单栋、单元或单个目标点。它们共用既有地图导入、地图标记、组件属性、自动路线和引导式部署 UI；不创建第二套地图编辑器。

所有生成内容仍为项目内的实验预览和下载 ZIP。它不会写入 `/opt/ry/data/tasks/multi_tasks`、机器人任务目录、行为树运行目录、定位运行配置，也不会调用 ROS、Supervisor 或任务服务。现场人工确认后，才可按既有现场流程把 ZIP 的 `multi_tasks/<community>/` 内容安装到运行目录。

## 选择与兼容

### 项目模式

创建项目的第一步增加必选模式：`single` 或 `multi`。模式保存为项目的不可变 `task_mode`：

- `single` 使用既有单任务点编译 Profile；
- `multi` 使用新的多任务点编译 Profile；
- 已有项目读取时迁移为 `single`，保持已有项目、接口和历史 ZIP 的行为；
- 项目创建完成后不提供模式切换。切换车辆模式必须创建一个新部署项目，避免混入两类车的任务产物。

模式选择是现有“新建部署项目”区域唯一新增交互。后续引导步骤、全局侧栏、地图工作区和组件编辑器维持原有视觉结构与行为。

### 共享地图事实

后端是路线、输出名称和文件树的唯一权威。浏览器不能提交路径、任务文件名、目标顺序、子任务顺序或输出目录。

现有地图实例和定位绑定作为输入事实：

- `building`、`unit` 与 `floor` 标识物理位置；
- `outdoor`、`lobby`、`typical_floor`、`floor_override` 地图角色描述地图用途；
- `typical_floor` 表示标准用户楼层模板；
- `floor_override` 表示非标准的具体物理楼层；
- 定位绑定继续描述地图类型和布局模板，不将运行时路径或手填路线写入项目。

地图归属由 Backend 固定派生：`ferry` 是整个小区唯一的全局地图；`outdoor`、`lobby`、
`typical_floor` 与 `floor_override` 都属于明确的楼栋/单元。户外任务文件名本身带
`<building>_<unit>`，因此不同栋单元的户外图不得被压缩为同一全局地图。

实施人员只需创建项目、选择模式、配置项目场景地图、导入地图并完成核心标记。系统自动推导经过顺序、共享段和目标分支。

## 场景流程与目录派生

`deployment_flow` 是生成目录的唯一阶段依据。只有实际存在的阶段才会生成相应目录或文件：

| 场景阶段 | 多任务 ZIP 产物 | 生成条件 |
| --- | --- | --- |
| `ferry` | `multi_tasks/<community>/sub_outdoor_eguard.json` 与 `_r.json` | 流程包含摆渡层，且该段地图、路径与组件完整 |
| `outdoor` | `multi_tasks/<community>/outdoor/<building>_<unit>.json` 与 `_r.json` | 流程包含户外阶段，且对应栋单元具有完整户外地图段 |
| `lobby` | `multi_tasks/<community>/indoor/<building>_<unit>.json` 与 `_r.json` | 对应栋单元具有完整大厅地图段 |
| `target_floor` | `multi_tasks/<community>/floor/...` | 对应用户楼层地图存在有效目标点 |

因此，只有“电梯大厅 → 用户楼层”的项目只生成 `indoor/` 和 `floor/`，不会生成 `sub_outdoor_eguard*` 或 `outdoor/`。流程有摆渡层才生成摆渡文件；流程有户外层才生成 `outdoor/`。缺失的非流程阶段不会造成报错或空目录；流程要求但地图、组件或路线不完整的阶段必须阻断预览，给出受控中文原因。

对每个栋单元，后端从场景顺序归集一条共享路线族：可选摆渡、可选户外、大厅、进入相应用户楼层。用户楼层的每个目标点是该路线族的一个末端分支，彼此不需要人工排序。

## 多目标点与房号语义

目标组件存储完整房号。例如地图实例物理楼层为 `15` 时，目标 `1501` 的业务语义固定为：

```text
floor = 15
door  = 01
```

后端必须通过目标完整房号和所属地图实例的物理楼层一致性校验得到此结果；不得通过“截取最后两位”的不透明规则猜测。房号格式或物理楼层不一致时阻断预览。

每个目标点有一条独立的去返配送分支：公共段和该目标对应的最终楼层段一起构成完整路线。标记两个目标 `1501`、`1502` 时，自动派生两个分支；不会允许浏览器为它们排序，也不会让一个目标覆盖另一个。

### 标准楼层模板

当目标所属地图实例角色为 `typical_floor`，为每个目标生成：

```text
floor/<building>_<unit>_n_n<door>.json
floor/<building>_<unit>_n_n<door>_r.json
```

例如 `1` 栋 `1` 单元的 `1501` 与 `1502` 分别生成：

```text
floor/1_1_n_n01.json
floor/1_1_n_n01_r.json
floor/1_1_n_n02.json
floor/1_1_n_n02_r.json
```

`01`、`02` 是户号。R6B 在运行时传入业务 `floor` 和 `door`，由既有目录规则将标准模板复用于同一布局的不同物理楼层。

### 非标准物理楼层

当目标所属地图实例角色为 `floor_override`，为每个目标生成：

```text
floor/<building>_<unit>_<physical_floor>_<full_room_number>.json
floor/<building>_<unit>_<physical_floor>_<full_room_number>_r.json
```

例如 `1` 栋 `1` 单元五层 `501` 生成：

```text
floor/1_1_5_501.json
floor/1_1_5_501_r.json
```

一个派生输出相对路径只能属于一个目标分支。任何同名碰撞、目标房号无效、文件对缺失或不能形成安全执行链都必须拒绝生成；不得覆盖、合并或猜测。

## 编译器与审计模型

新增两个明确的、纯函数式编译入口：

1. 单任务点编译器：对每条目标分支完整展开公共段与用户层段，生成单个目标对应的完整任务 JSON、相关行为树、定位产物和清单项。
2. 多任务点编译器：每栋单元的公共段各输出一次；用户楼层按目标输出正返程文件对；同时生成其所需的行为树、定位产物、任务状态码注册表副本和清单项。

两者都以同一份受控 SiteProject、相同的组件执行链、虚拟墙、地图编辑和任务状态码注册表为输入。受控设施行为树仍只在语义动作所在段插入；行为树文件名由稳定的业务语义生成，不能泄露随机组件 ID。

为支持多目标，后端派生“配送路线族”审计模型：每个栋单元记录一条共享地图顺序和公共执行节点；每个目标记录目标组件、房号语义、最终地图执行链及返程链。该模型由 Backend 生成并保存为预览输入快照，PC 仅展示人类可读的地图、目标和执行动作。既有 `localization_routes` 继续作为地图切换与定位清单的受控基础事实；多目标任务分支不能要求用户手填多套定位路线。

每个预览的 `manifest.json` 至少包含：

- 编译 Profile、版本、任务模式与完整输入 SHA-256；
- 所有产物相对路径和 SHA-256；
- 路线族、栋单元、阶段、目标完整房号、业务楼层和户号；
- 地图、组件、虚拟墙、地图编辑、定位模板和状态码注册表的受控输入指纹；
- `robot_runtime_changed: false` 与实验包声明。

ZIP 只能写入已验证的相对路径；下载名由项目名和模式派生，不接受浏览器提供的文件名。生成预览及 ZIP 均通过项目目录内临时文件原子落盘。

## HTTP、PC Web 与契约

现有任务编译预览和下载路由保持项目 ID 边界，预览请求仍为空对象，不接收输出路径。项目创建请求增加受控模式字段，后端必须严格枚举校验；任务编译配置继续只接收小区名称。

`shared/contracts/deployment.md` 必须更新为 Existing：

- 项目 `task_mode` 的创建、不可变性和历史兼容；
- 单任务点、多任务点的多目标语义；
- 场景阶段到多点 ZIP 目录的条件映射；
- 标准层与非标准层文件命名、`1501 → floor 15 / door 01` 规则；
- 项目内实验导出和运行时目录隔离；
- Backend 为唯一写入者、PC 为只读预览消费者、Mobile 非消费者。

PC 页面保持当前引导式交互与布局，仅在项目创建处显示模式选择，并在导出预览中以业务名称呈现“完整任务”或“公共段 / 用户楼层子任务”，不显示内部 UUID、组件 ID、散列或运行时路径。

## 错误与安全规则

- 项目模式不匹配、不完整阶段、未标记核心组件、目标房号不一致、无法到达的组件、输出文件名碰撞、缺少正返程路径、无效状态码注册表或无效地图快照均阻断预览；
- 历史单目标项目在未新增目标点时保持原有单文件内容与命名；任一单任务点项目新增多个有效目标点后，按每个目标生成一份完整任务，且不改变已有目标的输出命名；
- 不读取现有运行目录内容来修改或覆盖任务，不在预览过程中写入任何外部目录；
- 不新增 ROS、Supervisor、任务服务或浏览器直连机器人控制接口；
- 任何组件、虚拟墙、地图编辑、目标点、地图实例或场景阶段的变更都使预览失效，下一次预览必须重新派生。

## 验证策略

Backend：

1. 历史项目迁移为 `single`，既有单目标单任务编译快照保持不变。
2. 单任务点模式多个目标输出多份完整、独立的任务 JSON。
3. 多任务点模式多个目标只增加各自 `floor` 正返程对，公共段不重复。
4. 仅大厅到用户楼层时 ZIP 只含 `indoor/` 与 `floor/`；存在摆渡或户外阶段时才出现相应产物。
5. 标准层 `1501`、`1502` 生成 `n_n01`、`n_n02` 并记录 `floor=15`、`door=01/02`。
6. 覆盖层 `501` 生成显式 `5_501` 文件对。
7. 输出撞名、房号/楼层不匹配、缺少组件、断开的自动路径、无效文件对和状态码配置均安全失败。
8. ZIP 路径、清单散列、原子项目预览持久化和“不写运行目录”边界均有测试。

Web：

1. 创建项目显示两种模式并将选项锁定为只读事实。
2. 两种模式沿用既有向导、侧栏和地图工作区；不出现第二套地图标记 UI。
3. 导出预览只显示可读的地图段、楼栋单元、楼层和户号；不泄露内部标识。

完成前运行 `scripts/test-backend.sh`、`scripts/test-web.sh` 与 `git diff --check`。
