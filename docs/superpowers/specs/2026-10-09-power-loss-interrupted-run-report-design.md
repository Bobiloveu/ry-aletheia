# 断电中断测试的部分报告设计

## 目标

普通循环测试在小车断电、系统崩溃或进程被强制终止后，保留已完成轮次与已写入的轨迹证据，并在控制台下次启动时自动归档一份部分报告。

此设计只恢复审计记录，不恢复任何执行行为。系统不得在启动后继续未完成轮次、重连后补发任务、发布 ROS 指令，或将中断轮次伪装为通过或失败。

## 范围与非目标

适用对象为 RunManager 管理的普通单任务循环测试和顺序测试。部署验收已有独立持久化与重启处置模型，不改变其数据文件或状态机。

不尝试保存内存中的 ROS 客户端、线程、取消事件或进行中的服务调用。断电发生时正在执行的轮次没有可信终态，因此只能记录为结果未知。

重启后不增加新的阻塞确认步骤。控制台显示非阻塞提示；后续创建测试仍使用现有前置检查和安全边界。

## 状态模型

新增运行终态 interrupted，表示控制台从未结束检查点恢复，并已将未确认的当前轮归类为 unknown_after_power_loss。

unknown_after_power_loss 不是失败、不是通过，也不计入通过率。部分报告的结论为“意外断电中断”，并单列：

- 最后成功持久化的北京时间；
- 已完成、通过、失败、取消和结果未知的轮次数；
- 被中断的轮次序号；
- 已保存轨迹证据与缺失证据说明。

若断电发生在轮次之间，则不虚构未知轮次，只将整个运行标记为 interrupted。

## 检查点

每个活动运行在报告目录下保存一个隐藏检查点，路径固定且不被报告列表当作报告展示。检查点包含：

- schema 与运行 ID；
- 冻结的用例摘要、请求轮数、间隔和开始时间；
- 当前运行状态、活动轮次和最后保存时间；
- 已经确认的 AttemptResult；
- 每轮已生成的轨迹 JSON/SVG 引用及其报告目录边界；
- 运行错误、人工处置和前置检查摘要；
- 当前轮是否已开始但尚未取得可信终态。

检查点在以下边界更新：

1. 创建运行并登记后；
2. 进入一轮前；
3. 一轮产生可信结果并完成其轨迹证据写入后；
4. 进入或离开人工恢复、取消和其他终态时；
5. 部分报告成功归档后删除。

写入使用同目录临时文件、文件 fsync、原子替换和目录 fsync。读取必须校验 schema、字段类型、运行 ID 与所有路径都位于报告根目录。无效检查点不被用于生成报告，并留下明确的诊断记录。

## 启动恢复与归档

RunManager 初始化时仅扫描自己的检查点目录：

1. 忽略已终态或已归档的记录；
2. 将活动检查点转为内存中的 interrupted 运行；
3. 若检查点指示活动轮次已开始但无可信结果，追加一条 unknown_after_power_loss 记录；
4. 基于冻结数据和已存在证据生成一份部分报告；
5. 报告原子写入成功后删除该检查点。

若报告写入失败，检查点保留，下一次启动重试。重复启动不得产生多份同一运行的中断报告：报告文件名和恢复标记必须与运行 ID 绑定，并在写入前复核已有归档。

启动恢复不得实例化 RobotGateway、任务执行器、ROS 客户端或返回信号桥。它只读取检查点和已归档的轨迹文件。

## 页面与契约

现有运行状态响应增加 interrupted，轮次结果增加 unknown_after_power_loss。前端展示非阻塞的中断提示、部分报告入口，以及“结果未知，不计入通过率”的统计文案。

这是跨 Web 和 Backend 的公开运行状态变更。shared/contracts 需说明新增状态、统计规则和恢复边界；Mobile 若消费该运行状态，必须验证其未知状态降级展示。

## 验证

实现必须以回归测试覆盖：

- 已完成 8 轮、进行第 9 轮时断电：重启后生成一份部分报告；
- 第 9 轮仅为结果未知，未计入通过率；
- 已完成轮次的轨迹证据保留且只能引用报告根目录内文件；
- 断电发生在轮次之间时不创建虚构轮次；
- 部分报告写入失败后保留检查点并能在下次启动重试；
- 多次重启只生成一份同一运行的部分报告；
- 恢复路径没有调用 ROS、任务执行、导航或车辆控制接口；
- API、Web 与任何受影响 Mobile 消费者按契约处理新状态。

验证限于本地定向测试和受影响模块检查；不会编译、打包、升级或部署到小车。
