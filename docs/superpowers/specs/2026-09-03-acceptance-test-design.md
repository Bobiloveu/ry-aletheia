# 部署验收（Acceptance Test）设计说明

**日期：** 2026-09-03
**状态：** 待评审
**范围：** 仅新增桌面 Web「部署验收」模块；复用既有任务执行、ROS、轨迹、恢复、设置和报告能力。

## 1. 目标与边界

部署验收用于机器人本机在已部署的正式业务任务中，按小区或楼栋生成可复现、覆盖优先的随机验收计划，并逐项执行和留存证据。

本次不新增 ROS 节点、ROS service 调用、任务 JSON 生成/编辑、导航控制协议、视频链路、移动端页面或新的测试执行器。验收模块是既有执行能力之上的**计划编排层**。

正式任务目录固定为设置中的 `task_directory`（默认 `/opt/ry/data/tasks/origin_tasks`）。它只读：验收代码不得创建、写入、重命名或删除其中的文件。

第一版支持：

- 一个小区的全部任务验收；
- 一个小区内指定楼栋的验收；
- 全量或覆盖优先的抽样计划；
- 失败后的人工恢复、继续、取消、恢复中断计划；
- 可下载的验收报告与轨迹证据。

架构预留单元、楼层、自定义范围和失败项复测，但本次不暴露对应 UI 或 API。

## 2. 现有能力与复用关系

| 现有能力 | 责任 | 验收模块的用法 |
| --- | --- | --- |
| `CaseStore` / `TestCase` | 普通用例库和既有数据模型 | 仅复用 `TestCase`、`TaskParameters` 等稳定模型；不改变普通用例解析规则。 |
| `RobotGateway` | Supervisor 前置检查、依赖、任务可用性同步 | 每个验收任务继续使用既有 preflight / sync 逻辑。来源文件本来就在正式任务目录时，保持“同名文件存在，不覆盖”的安全行为。 |
| `RosTaskExecutor` | 唯一 ROS2 任务执行入口 | 继续执行已解析的 `TaskParameters`；不创建第二套 ROS executor。 |
| `RunManager` | 互斥、执行循环、取消、人工恢复、轨迹、普通测试报告 | 新增受控的“冻结任务序列”执行入口，与普通 run 共用活动态互斥锁、恢复流程和轨迹采集。原有 `start(case, ...)` 行为不变。 |
| `SettingsStore` | 通用运行配置 | 仍提供正式任务目录；验收阈值和计划状态由专用持久层保存，避免把运行账本塞进 `console.json`。 |
| 静态 Web 壳层 | 当前桌面控制台导航、暗色工业化操作界面 | 增加一个独立页面和导航项；不改 Flutter / mobile 页面。 |

## 3. 目录扫描与正式任务目录

新增 `AcceptanceTaskCatalog`，按需扫描正式任务目录，在内存中建立只读索引。扫描不会改动任何源文件。

### 3.1 文件筛选与名称解析

只接受普通 `.json` 文件；跳过隐藏文件、临时文件及名称中匹配 `_bak_`、`_backup`、`_old_`（不区分大小写）的明显非正式文件。其他可疑文件不静默消失，而是作为无效记录/扫描警告返回，便于现场发现问题。

解析基名时从右向左取最后四个数值字段：

`<community>_<building>_<unit>_<floor>_<door>.json`

因此小区名称可带下划线。前四段之外的所有部分组成 `community`。四个末尾字段必须能解析为非负整数，否则该文件不参与正式任务池，并携带原因。

### 3.2 内容与一致性检查

每条索引项包含：

`file_path`、`filename`、`community`、`building`、`unit`、`floor`、`door`、`task_group_name`、`valid`、`warnings`、`sha256`。

有效任务要求 JSON 顶层为对象，且存在非空 `subtasks` 数组。`task_group_name` 缺失或与文件名语义明显不同只产生 warning；验收范围始终以**文件名**为准。

`sha256` 是计划冻结时的源文件指纹。开始某项前若其文件不存在或指纹已经变化，计划进入阻塞状态，不会执行一个和冻结计划不一致的业务任务。

## 4. 验收计划与持久化

新增 `AcceptancePlanStore`，将计划、结果、人工恢复记录和报告关联信息，以原子写入方式保存在 `config/acceptance/`。进程/浏览器重启后能够恢复展示。

计划至少包含：

- `plan_id`、`created_at`、`updated_at`；
- `scope_type`（`community` / `building`）、`community`、可选的物理楼宇单元 `building + unit`；
- 冻结的 `task_pool` 摘要和 `selected_tasks` 快照（含路径、参数、文件指纹）；
- `planned_order`、服务端生成的 `random_seed`、`current_index`；随机种子仅保留在本地持久化与离线审计报告，不进入公共 API 或页面；
- `status`、每项执行/恢复结果、人工干预次数；
- `criteria_snapshot`；
- `run_id`、轨迹和验收报告的安全引用。

计划生成后，执行过程中不会重扫后重排；刷新页面也不会更换任务或种子。重新抽样只能明确创建/替换一个尚未开始的草稿计划；已运行计划只能继续、取消或归档。

### 4.1 状态机

`draft -> ready -> running -> awaiting_recovery -> recovering -> running -> completed`

另有 `cancelled`、`blocked`、`interrupted`。

- 单项失败会先记录失败和轨迹证据，进入 `awaiting_recovery`，不自动跳过。
- 操作员确认已人工恢复后，重跑既有前置检查；通过后才进入下一项。
- 后端重启时，任何 `preparing` / `running` / `awaiting_recovery` / `recovering` 计划都标为 `interrupted`，当前任务标记为“结果未知”。系统**绝不**自动再次下发该任务。
- 操作员必须在页面确认“已核对现场”，再选择结束该项为人工失败或继续既有恢复流程；确认后才可继续。
- `cancelled` / `blocked` / `interrupted` 是执行状态，不生成正式 PASS/FAIL 结论。

## 5. 覆盖优先随机

候选任务先按稳定字段排序，再用服务端保存的随机种子生成可复现的打散优先级。算法只使用冻结候选池，不依赖浏览器随机数。

- **小区范围**：优先补齐不同物理楼宇单元（`building + unit`），其次该单元内的楼层、户；对已选择分布稀疏的类别给更高分，并对同一物理楼宇单元/楼层连续出现施加惩罚。
- **指定范围**：一次只选择一个物理楼宇单元，并优先补齐该单元内的楼层、户。
- **全量模式**：选择候选池全部有效任务，仅使用该排序来降低连续相邻任务的空间集中度。
- **抽样模式**：由用户指定受限于候选池大小的数量，按照上述排序取前 N 项。

抽样是代表性验收，不是对上千户小区的住户普查。计划预览展示本次实际覆盖的物理楼宇单元、楼层、户数量；不因抽样未覆盖每层或每户产生告警。候选文件无效、正式任务目录为空等真实异常才告警。

## 6. 执行编排与互斥

`AcceptanceOrchestrator` 只管理计划状态和持久化，调用 `RunManager` 的受控序列执行能力。

`RunManager` 新增内部序列入口，逐项传入冻结 `TestCase`：

1. 与普通测试使用同一个 active-run 判定与 execution lock；任务执行、手动控制、场景改动、升级继续遵守现有互斥边界；
2. 每项继续执行既有 scene apply、preflight、任务同步、ROS 调用、轨迹采集和安全收尾；
3. 失败人工恢复复用既有恢复逻辑，但恢复函数接收“当前项 case”，不能错误地按第一项 case 恢复；
4. 每项轨迹写入既有安全的 reports 目录，并在验收计划中记录引用；
5. 验收模式不改写普通 run 的报告结构或普通 API 响应；验收报告由专用 writer 汇总多任务结果。

不增加任何新 ROS 通信层。验收运行和普通运行不能并行；若已有活动 run，启动验收返回明确冲突；反之亦然。

## 7. 验收标准与结论

标准与执行器分离，保存在可配置的验收标准配置中。每次生成计划都复制成 `criteria_snapshot`；以后修改标准不会篡改历史计划结论。

实施人员不填写通过率、覆盖率、允许失败数或人工干预阈值。覆盖率仍以 planned、executed、passed 三层记录并在报告中呈现，但它是自动计算的事实信息，不是人为配置的判断门槛。

固定判定规则为：冻结计划内**所有**任务通过，才得到通过；任一任务未通过，即为不通过。抽样模式显示“本次抽样通过 / 不通过”、自动通过率和实际覆盖的物理楼宇单元/楼层/户数量；它必须明确不代表全小区全量验收。全量模式沿用相同的“计划内任务全部通过”规则。

## 8. API 与前端

新增桌面 Web API，全部由后端鉴权/状态检查；不接受任意文件路径，也不把 ROS 控制暴露给浏览器：

- `GET /api/acceptance/catalog`：返回目录、有效任务及 warnings；
- `GET/PUT /api/acceptance/criteria`：读取/校验验收标准；
- `POST /api/acceptance/plans`：按实际 catalog 生成预览计划；
- `GET /api/acceptance/plans/current`、`GET /api/acceptance/plans/{id}`；
- `POST /api/acceptance/plans/{id}/reroll`：仅草稿/未开始计划；
- `POST /api/acceptance/plans/{id}/start`、`resume`、`cancel`；
- `POST /api/acceptance/plans/{id}/resolve-interruption`：显式处理重启时的未知项；
- `GET /api/acceptance/plans/{id}/report`：仅下载该计划安全引用的验收报告。

无效范围、越界抽样、非法状态转换返回 4xx；与已有运行冲突返回 409；不会用“成功 HTTP 返回”掩盖 ROS/执行失败。

新增 `acceptance-test.html` 及对应 JS/CSS，并在现有桌面壳层加入“部署验收”入口。页面采用现有深色工业化操作界面的间距、表单、状态色和行动层级，不改视觉体系。

页面顺序：

1. 范围：从 catalog 下拉选择小区，再选择小区/楼栋范围；展示真实可用任务池和扫描警告；
2. 计划：全量/抽样、数量、覆盖预览、随机种子、任务顺序与文件 warning；生成后必须再次确认才可开始；
3. 运行：当前项、状态、已完成/失败/待恢复、取消与人工恢复确认；
4. 标准与结果：可编辑阈值（保存后只影响新计划）、覆盖矩阵、结论、报告下载。

响应式只保证该桌面页面在窄浏览器内可读可操作；本次不修改 Flutter/mobile 路由、应用或现有手机接口。

## 9. 报告、清理与安全

`AcceptanceReportWriter` 产出专用 HTML + CSV，内容包括：冻结计划、源文件指纹、范围、随机种子、执行时间线、单项结果、人工干预、planned/executed/passed 覆盖、标准快照、结论和轨迹证据链接。

报告文件名使用固定受限格式（含 plan id），下载和删除只接受后端创建的安全引用。验收归档/删除绝不通过泛化路径删除普通 run 资产或正式任务文件；轨迹仅在计划明确归档后按其保存引用清理。

## 10. 测试与验收清单

实施采用测试优先，至少覆盖：

- 含下划线小区名的右向解析、过滤、无效 JSON、空 `subtasks`、task group warning；
- 全小区/指定楼栋过滤，固定种子可复现，抽样覆盖优先和覆盖不足警告；
- 计划原子持久化、重启中断标记、指纹变更阻塞；
- 未配置阈值的 CONDITIONAL_PASS、已配置阈值的 PASS/FAIL、三层覆盖统计；
- 普通 run 与验收 run 双向互斥；失败—人工恢复—继续、取消和不自动重发；
- API 输入校验、状态冲突和报告路径安全；
- 既有 backend/web 测试、前端生产构建及改动 API 契约检查。

需要实车验证的项目单列，不在本地模拟中假称已经完成：正式任务目录权限、任务同步的同名文件行为、失败后的现场人工恢复、轨迹资产可访问性、长计划下的 ROS/service/导航可靠性。

## 11. 明确不做的事项

- 不修改 `/opt/ry/data/tasks/origin_tasks` 的内容或命名；
- 不替代/重写 `RosTaskExecutor`、`RobotGateway`、`RunManager`、视频、MediaMTX、WebRTC、手动控制或急停；
- 不为验收另起 ROS node、线程池或浏览器直连 ROS；
- 不改变普通测试、报告、场景方案及 Flutter/mobile 的现有语义；
- 不根据未确认的“经验值”自动判定正式通过。
